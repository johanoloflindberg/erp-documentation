## What to Include in Your Support Request

A complete support request helps the team diagnose your issue without follow-up questions. Include all of the following that apply to your issue.

### Essential Information

<Steps>
  <Step title="Describe the problem clearly">
    Explain what you expected to happen and what actually happened. Be specific: "I POSTed to `/api/resource/Customer` with a valid payload and received a 400 error" is more useful than "the API doesn't work."
  </Step>
  <Step title="Include the request details">
    Provide the full HTTP request:
    - Method and URL (e.g. `POST https://your-instance.webbab.se/api/resource/Customer`)
    - Request headers (redact your API secret — include only the key)
    - Request body (the full JSON payload)

    ```
    POST /api/resource/Customer HTTP/1.1
    Host: your-instance.webbab.se
    Authorization: token YOUR_API_KEY:[REDACTED]
    Content-Type: application/json

    {"customer_name": "Acme AB", "customer_type": "Company"}
    ```
  </Step>
  <Step title="Include the full response">
    Provide the complete HTTP response:
    - HTTP status code
    - Response headers
    - Full response body (including any stack trace or error message)

    ```json
    HTTP/1.1 400 Bad Request

    {
      "exc_type": "MandatoryError",
      "message": "customer_group is mandatory"
    }
    ```
  </Step>
  <Step title="Include the request ID">
    WEBBAB assigns a unique identifier to every API request. Find this in the response headers (look for `X-Request-Id` or a similar header — TODO verify the exact header name for your WEBBAB instance). The request ID allows support to locate the exact request in server logs.
  </Step>
  <Step title="Specify your environment">
    State clearly whether the problem is occurring in production or staging, and provide your instance base URL (not your credentials).
  </Step>
</Steps>

### Additional Context

- **When did the issue start?** — Was it working before? What changed (code deployment, configuration change, credential rotation)?
- **Is it consistent or intermittent?** — Does it fail every time, or only occasionally?
- **Affected scope** — Is every API call affected, or only specific DocTypes, fields, or operations?
- **Your integration language / framework** — Helps the team spot client-side issues

## How to Find Request IDs

WEBBAB includes a request ID in the response headers for every API call. Capture it in your HTTP client logs:

```bash
# Include -v for verbose output that shows response headers
curl -v https://your-instance.webbab.se/api/resource/Customer \
  -H "Authorization: token YOUR_API_KEY:YOUR_SECRET" 2>&1 | grep -i "x-request"
```

## Reporting Security Issues

If you believe you have discovered a security vulnerability in WEBBAB — including authentication bypasses, data isolation failures, injection vulnerabilities, or credential exposure — do not report it through the standard support channel.

<Warning>
  **Security issues must be reported through the responsible disclosure channel.** Do not create a public ticket or post details in community forums.
</Warning>

- **Security email:** TODO — add security disclosure email address
- **What to include:** A clear description of the vulnerability, steps to reproduce, the potential impact, and whether you have already reported it elsewhere
- **What not to include:** Do not attempt to access data you do not own, do not run automated exploitation tools, and do not disclose the issue publicly until WEBBAB has had a reasonable opportunity to respond

WEBBAB will acknowledge your report and keep you informed of the investigation and remediation timeline.

## Escalation Process

For issues that are blocking your integration or causing production outages:

1. Open a support ticket through the standard channel and mark it as **urgent** or **production-impacting**
2. Include a business impact statement: what is broken, how many users or processes are affected, and the cost of continued downtime
