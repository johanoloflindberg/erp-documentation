## Current State

The WEBBAB API is built on Frappe Framework, which does not currently use version prefixes in its standard resource and method URL paths. There is no `/api/v1/resource/…` or `/api/v2/method/…` namespace today. The stable API surface is:

```
/api/resource/{DocType}
/api/resource/{DocType}/{name}
/api/method/{dotted.python.path}
```

This means all current integrations target the same unversioned endpoint namespace. When WEBBAB introduces a versioning scheme, existing integrations built against the unversioned paths will be handled according to the migration policy described below.

## Planned Versioning Approach

When WEBBAB introduces explicit API versioning, the intent is to follow a **URL path versioning** model:

```
/api/v1/resource/{DocType}
/api/v2/resource/{DocType}
```

Each major version will represent a stable, independently supported API surface. Minor and patch updates within a version will be backwards-compatible.

## What Counts as a Breaking Change

A **breaking change** is any modification that requires you to update your integration code to prevent failures. WEBBAB treats the following as breaking changes:

- Removing an endpoint or HTTP method.
- Renaming a required request field.
- Changing the data type of an existing field (e.g. string to integer).
- Removing a field from a response object that was previously always present.
- Changing the meaning or semantics of an existing status code for a given endpoint.
- Changing authentication mechanisms in a way that invalidates existing credentials.

## What Is NOT a Breaking Change

The following changes are considered **backwards-compatible** and may be introduced without a version bump or deprecation notice:

- Adding new optional request fields.
- Adding new fields to a response object.
- Adding new endpoints or HTTP methods.
- Adding new HTTP status codes that were not previously returned (integrate defensively).
- Improving error messages or `_server_messages` content.
- Performance improvements with no behavioral change.
- Bug fixes that make behavior consistent with documented intent.

<Tip>
  Build your integration to **ignore unknown fields** in response objects. This insulates you from additive changes and is a standard defensive coding practice.
</Tip>

## Handling Version Transitions

When a new API version is announced, follow this general upgrade approach:

1. **Read the migration guide** before making any code changes.
2. **Identify affected endpoints** in your integration by searching for deprecated field names or URL patterns.
3. **Test against the new version** in a staging environment or using a dedicated test instance.
4. **Deploy the updated integration** before the sunset date with a rollback plan.
5. **Remove any compatibility shims** after confirming the new version is stable in production.
