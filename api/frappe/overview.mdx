The WEBBAB API is built on top of [Frappe Framework](https://frappeframework.com/), an open-source full-stack web framework that provides a built-in REST API, a role-based permission system, and a schema-driven data model called **DocTypes**. Understanding how Frappe structures its API helps you work effectively with WEBBAB endpoints, interpret errors, and debug access control issues without needing to treat each endpoint as a black box.

## Frappe's Data Model: DocTypes

Every data entity in WEBBAB — customers, orders, invoices, files — is defined as a **DocType**. A DocType specifies the schema (fields, types, validations, links) for a class of records, and each record is called a **Document**. Documents have a unique `name` field that serves as the primary key.

The REST API surface maps directly onto this model:

```
/api/resource/{DocType}          → the collection of all Documents of that type
/api/resource/{DocType}/{name}   → a single Document
```

This means if you know the DocType name, you already know the URL for every CRUD operation on that type. There is no per-resource routing logic — the same controller handles all DocTypes.

## Two API Styles

Frappe exposes two complementary HTTP API namespaces:

## The Permission Layer

Every API request runs through Frappe's permission engine before any data is accessed. The authenticated user must have the appropriate **DocType permission** (read, write, create, delete) for the operation to succeed. Permissions are defined at the role level, and users inherit permissions from all of their assigned roles.

A `403 Forbidden` response always means the user has valid credentials but lacks the required permission — it is not an authentication error. See [Permissions](/api/frappe/permissions) for a full explanation.

## Authentication and Session

WEBBAB API requests use token authentication (`Authorization: token key:secret`). Frappe supports multiple authentication mechanisms internally, but for API integrations, token auth is the recommended approach. Each API token is tied to a specific Frappe user account, and all operations performed via that token respect that user's role-based permissions.

See [Authentication](/api/authentication) for header format and credential management.

## Response Envelope

Frappe wraps API responses in a consistent envelope depending on the call type:

| Call type | Success envelope | Error envelope |
|---|---|---|
| Resource (list) | `{ "data": [ ... ] }` | `{ "exc_type": "...", "exception": "...", ... }` |
| Resource (single) | `{ "data": { ... } }` | `{ "exc_type": "...", "exception": "...", ... }` |
| RPC Method | `{ "message": ... }` | `{ "exc_type": "...", "exception": "...", ... }` |

See [Errors](/api/errors) for a complete breakdown of the error envelope structure.

## DocType Naming Conventions

DocType names are PascalCase (e.g. `Customer`, `Sales Order`, `Sales Invoice`). When they contain spaces, URL-encode them:

| DocType | URL-encoded path |
|---|---|
| `Customer` | `/api/resource/Customer` |
| `Sales Order` | `/api/resource/Sales%20Order` |
| `Sales Invoice` | `/api/resource/Sales%20Invoice` |

Document names are auto-generated by Frappe's naming series (e.g. `CUST-00001`, `SO-00001`) unless a custom naming rule is configured.
