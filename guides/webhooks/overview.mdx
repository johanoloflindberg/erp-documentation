Webhooks let WEBBAB push event notifications directly to your server the moment something happens — a record is created, updated, or deleted — without you having to poll the API. Instead of asking "did anything change?", WEBBAB calls you. This makes webhooks the right choice for building reactive integrations, near-real-time dashboards, and automated workflows.

## How WEBBAB Delivers Events

When a subscribed event occurs, WEBBAB sends an **HTTP POST** request to the endpoint URL you registered. The request body is a JSON payload describing the event. Your server must respond with an HTTP `2xx` status code within the timeout window to acknowledge successful delivery.

```
WEBBAB Platform
      │
      │  HTTP POST  application/json
      ▼
Your Webhook Endpoint (HTTPS)
      │
      │  HTTP 200 OK  (acknowledge within timeout)
      ▼
WEBBAB marks delivery as successful
```

## Payload Structure

Every webhook delivery shares a common envelope structure regardless of the event type. The `data` field contains the full document that triggered the event.

```json
{
  "event": "customer.created",
  "timestamp": "2024-11-15T10:32:00.000Z",
  "doctype": "Customer",
  "name": "CUST-00123",
  "data": {
    "name": "CUST-00123",
    "customer_name": "Acme Corp",
    "customer_type": "Company",
    "territory": "Sweden",
    "creation": "2024-11-15T10:32:00.000Z",
    "modified": "2024-11-15T10:32:00.000Z",
    "docstatus": 0
  }
}
```

| Field | Type | Description |
|---|---|---|
| `event` | string | Event name in `doctype.action` format |
| `timestamp` | string | ISO 8601 UTC timestamp of the event |
| `doctype` | string | The Frappe DocType that triggered the event |
| `name` | string | The unique document name (primary key) |
| `data` | object | Full document fields at the time of the event |

## Retry Policy

If your endpoint does not respond with a `2xx` status code — or times out — WEBBAB will retry the delivery automatically.

</Info>

| Attempt | Approximate delay |
|---|---|
| 1 (initial) | Immediately |
| 2 | ~1 minute |
| 3 | ~5 minutes |
| 4 | ~30 minutes |
| 5 | ~2 hours |

After all retry attempts are exhausted, the delivery is marked **failed** and no further attempts are made. You can inspect failed deliveries in the WEBBAB dashboard under **Integrations → Webhooks → Delivery Log**.

<Warning>
Design your endpoint to respond with `200 OK` as fast as possible — before doing any database writes, external HTTP calls, or heavy computation. Enqueue the payload to an internal job queue and acknowledge immediately to avoid unnecessary retries.
</Warning>

## Timeout Behaviour

WEBBAB closes the connection and treats a delivery as failed if your endpoint does not begin sending a response within the configured timeout. A slow DNS lookup, TCP handshake, or application boot time can all eat into this budget.

**Best practice:** Keep your webhook handler thin. Parse the JSON, validate the signature, enqueue the job, and return `200`. Aim for a response time under **500 ms**.

## Ordering Guarantees

WEBBAB does **not** guarantee that webhook events arrive in strict chronological order. Network conditions, retry timing, and parallel delivery workers can cause events to arrive out of order. Always treat events as independent notifications and use the `timestamp` field or fetch the current document state via the REST API when order matters.

## Security Model

Every webhook delivery is signed using **HMAC-SHA256**. The signature is sent in the `X-Frappe-Webhook-Signature` header, allowing you to verify that the request genuinely came from WEBBAB and that the payload was not tampered with in transit.

```
X-Frappe-Webhook-Signature: sha256=<hex-digest>
```

Always verify the signature before processing the payload. See [Verify Webhook Signatures](/guides/webhooks/authentication) for implementation details and code examples.

<Warning>
Only accept webhook deliveries over **HTTPS**. Plaintext HTTP endpoints cannot guarantee payload integrity even with signature verification.
</Warning>

## HTTPS Requirement

Your endpoint URL must use `https://`. WEBBAB will refuse to deliver events to plaintext `http://` URLs in production. During local development, use a tunneling tool such as [ngrok](https://ngrok.com) to expose a local HTTPS URL. See [Test Webhooks Locally](/guides/webhooks/testing) for a step-by-step guide.
