WEBBAB emits webhook events whenever documents in the platform change state. Each event corresponds to a lifecycle hook on a Frappe DocType — such as creation, update, submission, or deletion. Understanding the event naming convention and payload structure lets you build targeted integrations that react only to the changes you care about.

## Event Naming Convention

Events follow the pattern **`doctype.action`**, where:

- **`doctype`** is the lowercase, underscore-separated name of the Frappe DocType (e.g. `sales_order`, `customer`, `purchase_invoice`)
- **`action`** maps to the Frappe document lifecycle hook that triggered the delivery

| Action | Frappe Hook | Trigger condition |
|---|---|---|
| `created` | `after_insert` | A new document is saved for the first time |
| `updated` | `on_update` | An existing document field changes |
| `submitted` | `on_submit` | A document moves to the Submitted state |
| `cancelled` | `on_cancel` | A submitted document is cancelled |
| `deleted` | `on_trash` | A document is permanently deleted |

**Examples:**

```
customer.created       →  A new Customer was added
sales_order.submitted  →  A Sales Order was submitted
purchase_invoice.cancelled  →  An invoice was cancelled
contact.updated        →  A Contact record was changed
```

## Common Payload Structure

Every webhook delivery shares the same top-level envelope regardless of the event type:

```json
{
  "event": "customer.created",
  "timestamp": "2024-11-15T10:32:00.000Z",
  "doctype": "Customer",
  "name": "CUST-00123",
  "data": { ... }
}
```

| Field | Type | Description |
|---|---|---|
| `event` | string | Full event name in `doctype.action` format |
| `timestamp` | string | ISO 8601 UTC timestamp when the event was emitted |
| `doctype` | string | The DocType name in its original casing |
| `name` | string | The document's unique identifier (primary key) |
| `data` | object | Document fields included at the time of the event |

## Registering for Specific Events

When you [register a webhook](/guides/webhooks/registering), you specify both the `webhook_doctype` and `webhook_docevent`. To subscribe to multiple events on the same DocType, create one webhook subscription per event:

```jsonc
// Subscription 1 — Customer created
{
  "webhook_doctype": "Customer",
  "webhook_docevent": "after_insert",
  "request_url": "https://your-server.example.com/webhooks/webbab"
}

// Subscription 2 — Customer updated
{
  "webhook_doctype": "Customer",
  "webhook_docevent": "on_update",
  "request_url": "https://your-server.example.com/webhooks/webbab"
}
```

<Tip>
Use the `event` field in the delivered payload to route events to the appropriate handler within a single endpoint, rather than creating a separate URL for each event.
</Tip>

## Handling Unknown Events

WEBBAB may introduce new event types in future releases. Build your event handler to gracefully ignore events it does not recognise rather than throwing an error:

```javascript
app.post('/webhooks/webbab', (req, res) => {
  res.sendStatus(200); // Always acknowledge first

  const { event, data, name } = JSON.parse(req.body.toString());

  switch (event) {
    case 'customer.created':
      handleCustomerCreated(data);
      break;
    case 'sales_order.submitted':
      handleOrderSubmitted(data);
      break;
    default:
      console.log(`Unhandled event type: ${event} for ${name} — ignoring`);
  }
});
```
