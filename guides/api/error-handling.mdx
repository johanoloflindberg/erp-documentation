Every integration eventually encounters errors — invalid input, missing permissions, network blips, or server-side failures. Understanding the structure of WEBBAB error responses and the meaning of each HTTP status code lets you diagnose problems quickly and build integrations that recover gracefully without requiring manual intervention. This page explains the error format, status code semantics, and practical patterns for handling common failure scenarios.

## Error Response Structure

When a request fails, WEBBAB returns a non-2xx HTTP status code and a JSON body with details about the error. The shape of the response varies slightly by error type, but the most common fields are:

```json
{
  "exc_type": "ValidationError",
  "exception": "frappe.exceptions.ValidationError: Item Code is mandatory",
  "message": "Item Code is mandatory",
  "_server_messages": "[{\"message\": \"Item Code is mandatory\", \"indicator\": \"red\"}]"
}
```

<ResponseField name="exc_type" type="string">
  The Python exception class name. Use this to categorise the error type programmatically.
</ResponseField>

<ResponseField name="exception" type="string">
  The full exception string including the module path and message. Useful for debugging but not suitable for displaying to end users.
</ResponseField>

<ResponseField name="message" type="string">
  A human-readable error message. May be suitable for display in a developer UI after sanitisation.
</ResponseField>

<ResponseField name="_server_messages" type="string">
  A JSON-encoded array of message objects shown in the Frappe UI. Contains `message` and `indicator` fields. Parse this string if you need structured error messages.
</ResponseField>

## HTTP Status Code Reference

| Status Code | Name | Meaning and Common Cause |
|-------------|------|--------------------------|
| `400` | Bad Request | The request is malformed or fails validation. A required field is missing, a value is the wrong type, or a DocType constraint is violated. |
| `401` | Unauthorized | No credentials were provided, the `Authorization` header is missing, or the API key/token is invalid or expired. |
| `403` | Forbidden | The authenticated user does not have permission to perform the requested operation on this DocType or document. |
| `404` | Not Found | The requested DocType or document name does not exist, or the URL path is incorrect. |
| `405` | Method Not Allowed | The HTTP method (GET, POST, PUT, DELETE) is not supported for this endpoint. |
| `409` | Conflict | A duplicate document would be created (e.g., a record with the same unique field already exists), or the document is in a state that prevents the operation (e.g., a submitted document cannot be modified directly). |
| `429` | Too Many Requests | The rate limit has been exceeded. Back off and retry after the indicated wait time. See [Rate Limits](/guides/api/rate-limits). |
| `500` | Internal Server Error | An unexpected error occurred on the server. These errors are not caused by your request and are generally transient. |

## Handling Specific Error Types

### 400 — Validation Errors

Validation errors occur when your request data does not satisfy DocType rules. The `_server_messages` field usually lists each specific problem.

<CodeGroup>

```javascript JavaScript — parse validation errors
async function createDocument(doctype, data) {
  const response = await fetch(
    `https://your-instance.webbab.se/api/resource/${encodeURIComponent(doctype)}`,
    {
      method: "POST",
      headers: {
        Authorization: `token ${process.env.WEBBAB_API_KEY}:${process.env.WEBBAB_API_SECRET}`,
        "Content-Type": "application/json",
      },
      body: JSON.stringify(data),
    }
  );

  if (response.status === 400) {
    const error = await response.json();
    const messages = JSON.parse(error._server_messages || "[]");
    const humanMessages = messages.map((m) => m.message);
    throw new Error(`Validation failed: ${humanMessages.join(", ")}`);
  }

  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }

  return response.json();
}
```

```python Python — parse validation errors
def create_document(doctype: str, data: dict) -> dict:
    resp = requests.post(
        f"https://your-instance.webbab.se/api/resource/{doctype}",
        headers={
            "Authorization": (
                f"token {os.environ['WEBBAB_API_KEY']}"
                f":{os.environ['WEBBAB_API_SECRET']}"
            ),
            "Content-Type": "application/json",
        },
        json=data,
    )

    if resp.status_code == 400:
        error = resp.json()
        try:
            messages = json.loads(error.get("_server_messages", "[]"))
            reasons = [m["message"] for m in messages]
        except (json.JSONDecodeError, KeyError):
            reasons = [error.get("message", "Unknown validation error")]
        raise ValueError(f"Validation failed: {', '.join(reasons)}")

    resp.raise_for_status()
    return resp.json()["data"]
```

</CodeGroup>

### 401 — Authentication Errors

A `401` response means your credentials are missing or invalid. Check that:

1. The `Authorization` header is present and formatted as `token api_key:api_secret`.
2. The API key has not been revoked.
3. The token has not expired (for session-based auth).

### 403 — Permission Errors

A `403` response means the authenticated user lacks the required role or permission for the operation. Contact your WEBBAB administrator to review the roles assigned to your API user or service account.

```json
{
  "exc_type": "PermissionError",
  "exception": "frappe.exceptions.PermissionError: Not permitted",
  "message": "Not permitted"
}
```

### 404 — Not Found

Check that:
- The DocType name in the URL is spelled correctly and uses the exact casing WEBBAB expects.
- The document `name` you are requesting actually exists.
- URL path components with spaces are properly encoded as `%20`.

### 409 — Conflict

A `409` often means you are trying to create a document that already exists, or modifying a submitted document in a way that is not allowed. Check the `exc_type` field — common values are `DuplicateEntryError` and `ValidationError`.

### 500 — Server Errors

Server errors are not caused by your request. They are safe to retry with exponential backoff. If they persist, contact WEBBAB support with the request details and timestamp.

## Retry Logic

Implement automatic retries for transient errors (`429`, `500`, `502`, `503`, `504`). Do not retry `4xx` errors other than `429` — they indicate a problem with your request that a retry will not fix.

<CodeGroup>

```javascript JavaScript — retry with exponential backoff
async function requestWithRetry(url, options, maxRetries = 3) {
  const RETRYABLE = new Set([429, 500, 502, 503, 504]);

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (response.ok) {
      return response.json();
    }

    if (!RETRYABLE.has(response.status) || attempt === maxRetries) {
      const error = await response.json().catch(() => ({}));
      throw new Error(
        `Request failed (${response.status}): ${error.message || "Unknown error"}`
      );
    }

    // Exponential backoff: 1s, 2s, 4s, ...
    const retryAfter = response.headers.get("Retry-After");
    const delay = retryAfter
      ? parseInt(retryAfter, 10) * 1000
      : Math.pow(2, attempt) * 1000;

    console.warn(`Attempt ${attempt + 1} failed (${response.status}). Retrying in ${delay}ms…`);
    await new Promise((resolve) => setTimeout(resolve, delay));
  }
}
```

```python Python — retry with exponential backoff
import time

RETRYABLE_CODES = {429, 500, 502, 503, 504}

def request_with_retry(method: str, url: str, max_retries: int = 3, **kwargs) -> dict:
    headers = kwargs.pop("headers", {})
    headers["Authorization"] = (
        f"token {os.environ['WEBBAB_API_KEY']}:{os.environ['WEBBAB_API_SECRET']}"
    )

    for attempt in range(max_retries + 1):
        resp = requests.request(method, url, headers=headers, **kwargs)

        if resp.ok:
            return resp.json()

        if resp.status_code not in RETRYABLE_CODES or attempt == max_retries:
            resp.raise_for_status()

        # Honour Retry-After header if present, otherwise use exponential backoff
        retry_after = resp.headers.get("Retry-After")
        delay = float(retry_after) if retry_after else (2 ** attempt)
        print(f"Attempt {attempt + 1} failed ({resp.status_code}). Retrying in {delay}s…")
        time.sleep(delay)
```

</CodeGroup>

<Warning>
  Never retry `400`, `401`, `403`, or `404` responses automatically. These indicate problems with the request itself (bad data, missing auth, wrong URL) that will not resolve on retry and will only generate unnecessary load.
</Warning>

## Error Handling Checklist

<CardGroup cols={2}>
  <Card title="Check status code first" icon="circle-check">
    Always inspect the HTTP status code before parsing the response body. Status codes give you the fastest signal about what went wrong.
  </Card>
  <Card title="Log exc_type for debugging" icon="bug">
    Log the `exc_type` and `exception` fields to your error tracking system. They give specific context that `message` alone may not provide.
  </Card>
  <Card title="Sanitise before displaying" icon="eye-slash">
    The `exception` field contains internal stack traces. Never display it directly to end users — use the `message` field or a generic fallback message instead.
  </Card>
  <Card title="Implement idempotency" icon="rotate">
    For write operations, use [idempotency keys](/guides/api/idempotency) to safely retry requests after a network failure without risking duplicate records.
  </Card>
</CardGroup>
