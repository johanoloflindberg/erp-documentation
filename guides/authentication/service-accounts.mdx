A service account is a dedicated WEBBAB user that represents an application or automated process rather than a human being. Unlike regular user accounts, service accounts are not tied to any individual employee, do not have passwords that rotate with staff turnover, and can be granted precisely the permissions your integration needs — nothing more. They are the recommended credential pattern for any workload that runs without a human in the loop.

## When to Use a Service Account

Use a service account instead of a personal user's API key whenever:

- Your integration runs as a background job, cron task, or scheduled automation.
- You are connecting a third-party system (ERP, CRM, data pipeline) to WEBBAB.
- Your CI/CD pipeline needs to read or write WEBBAB data during deployments or tests.
- Multiple team members maintain an integration and you cannot tie it to one person's account.
- You want credentials that survive employee offboarding without disruption.

<Tip>
  Naming your service accounts descriptively — for example `svc-data-pipeline` or `svc-billing-sync` — makes it easier to audit access logs and identify which integration is responsible for a given request.
</Tip>

<Steps>
  <Step title="Create a new user">
    In your WEBBAB instance, navigate to **Settings → User List** (or **Home → Users**) and click **New User**. Enter a descriptive email address that identifies the service — for example `svc-inventory-sync@yourcompany.com`.
  </Step>
  <Step title="Set the account type">
    Set the user type to **System User** if the account needs access to all configured doctypes, or **Website User** if it only needs limited access. Disable the **Send Welcome Email** option to avoid sending onboarding emails to a non-person account.
  </Step>
  <Step title="Assign roles">
    Assign only the roles required for the integration (see [Assign Roles and Permissions](#assign-roles-and-permissions) below). Do not grant System Manager or Administrator roles unless absolutely necessary.
  </Step>
  <Step title="Generate an API key">
    Open the new user's profile, scroll to the **API Access** section, and click **Generate Keys**. Copy the `api_key` and `api_secret` immediately and store them in your secrets manager.
  </Step>
  <Step title="Disable password login">
    Remove or set a strong random password for the account and ensure direct password login is not needed. The account should authenticate exclusively via API key.
  </Step>
</Steps>

## Assign Roles and Permissions

The principle of least privilege is especially important for service accounts, because a compromised service account credential gives an attacker whatever permissions that account holds.

<CardGroup cols={2}>
  <Card title="Use custom roles" icon="user-gear">
    Create a dedicated role (for example `Integration - Inventory Read`) and grant only the doctype permissions the service account genuinely needs.
  </Card>
  <Card title="Avoid broad roles" icon="circle-xmark">
    Do not assign roles like **System Manager** or **Administrator** to a service account. These roles allow destructive or configuration-changing operations.
  </Card>
  <Card title="Read vs write" icon="pen-to-square">
    If the integration only reads data, grant read-only permissions. Reserve write, create, and delete permissions for integrations that genuinely need them.
  </Card>
  <Card title="Review regularly" icon="magnifying-glass">
    Audit service account permissions quarterly and remove access for any integration that is decommissioned or has changed scope.
  </Card>
</CardGroup>

### Example: Read-Only Integration

For a reporting pipeline that only reads Sales Order data, you might create a role called `Reporting Integration` with:

| DocType | Read | Write | Create | Delete | Submit |
|---------|------|-------|--------|--------|--------|
| Sales Order | ✅ | ❌ | ❌ | ❌ | ❌ |
| Customer | ✅ | ❌ | ❌ | ❌ | ❌ |
| Item | ✅ | ❌ | ❌ | ❌ | ❌ |

## Authenticate with Service Account Credentials

Service accounts authenticate using the same API key mechanism as regular users. Pass the `api_key` and `api_secret` in the `Authorization` header:

```
Authorization: token YOUR_API_KEY:YOUR_SECRET
```

<CodeGroup>

```bash cURL
curl --request GET \
  --url "https://your-instance.webbab.se/api/resource/Sales%20Order" \
  --header "Authorization: token YOUR_API_KEY:YOUR_SECRET" \
  --header "Content-Type: application/json"
```

```javascript JavaScript
const response = await fetch(
  "https://your-instance.webbab.se/api/resource/Sales%20Order",
  {
    method: "GET",
    headers: {
      Authorization: `token ${process.env.WEBBAB_SVC_API_KEY}:${process.env.WEBBAB_SVC_API_SECRET}`,
      "Content-Type": "application/json",
    },
  }
);
```

```python Python
import os
import requests

response = requests.get(
    "https://your-instance.webbab.se/api/resource/Sales Order",
    headers={
        "Authorization": (
            f"token {os.environ['WEBBAB_SVC_API_KEY']}"
            f":{os.environ['WEBBAB_SVC_API_SECRET']}"
        ),
        "Content-Type": "application/json",
    },
)
response.raise_for_status()
```

</CodeGroup>

For a full reference on header format and key management, see [API Key Authentication](/guides/authentication/api-keys).

## Store Credentials Securely

<Warning>
  Never commit service account credentials to source control. A single leaked key in a public repository can expose your WEBBAB data to anyone who finds it.
</Warning>

Store service account credentials using your platform's native secrets mechanism:

| Platform | Recommended Storage |
|----------|-------------------|
| GitHub Actions | [Encrypted Secrets](https://docs.github.com/en/actions/security-guides/encrypted-secrets) |
| GitLab CI | [CI/CD Variables (masked)](https://docs.gitlab.com/ee/ci/variables/) |
| AWS | AWS Secrets Manager or Parameter Store |
| Kubernetes | Kubernetes Secrets (ideally backed by an external vault) |
| Docker Compose | `.env` file excluded from version control via `.gitignore` |

## Rotate and Revoke Service Account Keys

Rotate service account keys on the same schedule as regular API keys — at minimum every 90 days, and immediately if a key is suspected to have been exposed.

<Steps>
  <Step title="Generate new keys">
    Navigate to the service account's user profile and generate a new API key pair.
  </Step>
  <Step title="Update all consumers">
    Update the credentials in every environment (production, staging, CI/CD) that uses this service account before revoking the old key.
  </Step>
  <Step title="Verify the new credentials">
    Run a test request against the API to confirm the new key works correctly.
  </Step>
  <Step title="Revoke the old key">
    Delete the old key from the user profile. It is immediately invalidated.
  </Step>
</Steps>

To fully decommission a service account, disable or delete the user in **Settings → User List**. All API keys for that user are revoked automatically.
