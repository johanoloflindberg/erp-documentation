Session-based authentication lets you log in with a username and password to establish a server-side session, then use that session to authenticate subsequent API requests. This approach is common in browser-facing integrations and interactive workflows where a human user is actively present. Unlike API keys, sessions are tied to a login event and expire after a period of inactivity or when the user logs out.

## How It Works

The session auth flow has three steps: log in with credentials to obtain a session, include the session cookie in every subsequent request, and handle expiry by logging in again when the session is no longer valid.

## Step 1 — Log In and Obtain a Session

Send a `POST` request to the login endpoint with the user's credentials. On success, WEBBAB sets a `sid` session cookie in the response, which your HTTP client carries automatically on subsequent requests.

<CodeGroup>

```bash cURL
curl --request POST \
  --url "https://your-instance.webbab.se/api/method/login" \
  --header "Content-Type: application/json" \
  --cookie-jar cookies.txt \
  --data '{
    "usr": "user@example.com",
    "pwd": "YOUR_PASSWORD"
  }'
```

```javascript JavaScript (fetch)
const response = await fetch(
  "https://your-instance.webbab.se/api/method/login",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    credentials: "include",
    body: JSON.stringify({
      usr: "user@example.com",
      pwd: process.env.WEBBAB_PASSWORD,
    }),
  }
);

const data = await response.json();
// The browser automatically stores the session cookie (sid)
// returned in the Set-Cookie response header
```

```python Python (requests)
import os
import requests

session = requests.Session()

response = session.post(
    "https://your-instance.webbab.se/api/method/login",
    json={
        "usr": "user@example.com",
        "pwd": os.environ["WEBBAB_PASSWORD"],
    },
)

response.raise_for_status()
# The requests.Session object stores the sid cookie automatically
print("Logged in:", response.json().get("message"))
```

</CodeGroup>

### Login Response

A successful login returns HTTP `200` with a JSON body:

```json
{
  "message": "Logged In",
  "home_page": "/",
  "full_name": "Example User"
}
```

<ResponseField name="message" type="string">
  Confirmation string. Value is `"Logged In"` on success.
</ResponseField>
<ResponseField name="full_name" type="string">
  Display name of the authenticated user.
</ResponseField>
<ResponseField name="home_page" type="string">
  Default redirect path for this user in the web UI.
</ResponseField>

The session is established via the `sid` cookie set in the `Set-Cookie` response header. Your HTTP client (browser or `requests.Session`) carries this cookie on all subsequent requests automatically.

<Warning>
  Never log or store raw credentials (`usr`/`pwd`) beyond the login step. Discard them from memory once the session is established.
</Warning>

## Step 2 — Authenticate Subsequent Requests

If you are using an HTTP client that manages cookies automatically (browser `fetch` with `credentials: "include"`, or a `requests.Session` in Python), the session cookie is sent automatically. If you need to pass the session explicitly, include it as a cookie header.

<CodeGroup>

```bash cURL — use stored cookie jar
curl --request GET \
  --url "https://your-instance.webbab.se/api/resource/Item" \
  --cookie cookies.txt \
  --header "Content-Type: application/json"
```

```javascript JavaScript (fetch)
async function fetchItems() {
  const response = await fetch(
    "https://your-instance.webbab.se/api/resource/Item",
    {
      method: "GET",
      credentials: "include",
      headers: {
        "Content-Type": "application/json",
      },
    }
  );

  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }

  return response.json();
}
```

```python Python (requests.Session)
def fetch_items(session: requests.Session) -> dict:
    response = session.get(
        "https://your-instance.webbab.se/api/resource/Item",
        headers={"Content-Type": "application/json"},
    )
    response.raise_for_status()
    return response.json()
```

</CodeGroup>

<Note>
  For server-to-server integrations that do not maintain a browser context, [API Key Authentication](/guides/authentication/api-keys) is simpler and more reliable than session-based login.
</Note>

## Step 3 — Handle Session Expiry

When a session expires or is invalidated, the API returns `HTTP 401 Unauthorized`. Your integration should detect this status code and re-authenticate automatically.

<CodeGroup>

```javascript JavaScript — auto-refresh example
async function requestWithRetry(url, loginFn) {
  let response = await fetch(url, { credentials: "include" });

  if (response.status === 401) {
    // Session expired — log in again and retry once
    await loginFn();
    response = await fetch(url, { credentials: "include" });
  }

  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }

  return response.json();
}
```

```python Python — auto-refresh example
def request_with_retry(session: requests.Session, url: str, login_fn) -> dict:
    response = session.get(url)

    if response.status_code == 401:
        # Session expired — re-authenticate and retry once
        login_fn(session)
        response = session.get(url)

    response.raise_for_status()
    return response.json()
```

</CodeGroup>

## Session Expiry Behaviour

<Info>
  **TODO** — The exact session lifetime and idle timeout need verification with the WEBBAB team. The guidance below reflects standard Frappe Framework behaviour and will be updated once confirmed.
</Info>

In standard Frappe deployments:

- Sessions expire after a configurable idle period (commonly 6–24 hours).
- There is no separate refresh token — you must log in again when the session expires.
- Logging out via `POST /api/method/logout` invalidates the session immediately.

If your use case requires long-lived programmatic access without re-entering credentials, consider using [API Key Authentication](/guides/authentication/api-keys) instead.

## Logout

To explicitly end the session, call the logout endpoint. Pass the session cookie (handled automatically if you use a cookie-aware client):

<CodeGroup>

```bash cURL
curl --request POST \
  --url "https://your-instance.webbab.se/api/method/logout" \
  --cookie cookies.txt
```

```javascript JavaScript
await fetch("https://your-instance.webbab.se/api/method/logout", {
  method: "POST",
  credentials: "include",
});
```

```python Python
session.post("https://your-instance.webbab.se/api/method/logout")
```

</CodeGroup>

## Choosing the Right Auth Method

<CardGroup cols={2}>
  <Card title="Session Login" icon="user">
    Best for interactive applications where a real user logs in. Sessions are scoped to a login event and invalidated on logout or timeout.
  </Card>
  <Card title="API Keys" icon="key">
    Best for server-to-server integrations and automation. Keys persist until explicitly revoked and do not require re-authentication. See [API Keys](/guides/authentication/api-keys).
  </Card>
</CardGroup>
