The synchronous integration pattern is the simplest way to connect WEBBAB to an external system: your code sends a request, waits for a response, and acts on it immediately. Because the caller blocks until the response arrives, this pattern is a natural fit for user-facing operations where you need the result before you can continue — such as looking up a customer before creating an order, or validating a product code at checkout.

## When to Use This Pattern

Choose the synchronous pattern when:

- **The result is needed immediately** — your workflow cannot proceed without the response (e.g. fetching a price before displaying it to a user)
- **Operations are short-lived** — the WEBBAB API call completes in well under a second
- **Simplicity is a priority** — you want straightforward code without queues, workers, or event brokers
- **Volume is modest** — you are not making hundreds of concurrent calls that could exhaust connection pools

Avoid it when:

- The operation may be slow (bulk imports, report generation)
- The caller cannot tolerate latency or temporary unavailability of WEBBAB
- You need to fan out to many WEBBAB endpoints in parallel

## Architecture

```
Your Application
      │
      │  HTTP GET/POST/PUT  (blocks, waits)
      ▼
WEBBAB REST API
      │
      │  JSON response
      ▼
Your Application continues
```

Every request-response cycle is **synchronous and sequential**. If WEBBAB is slow or unreachable, your application stalls until the timeout fires.

## How It Works

<Steps>
  <Step title="Authenticate">
    Obtain credentials and include them in every request via the `Authorization` header.
  </Step>
  <Step title="Send the request">
    Call the appropriate WEBBAB REST endpoint (`GET`, `POST`, `PUT`, or `DELETE`).
  </Step>
  <Step title="Await the response">
    Your thread or async function waits for WEBBAB to return a complete HTTP response.
  </Step>
  <Step title="Handle the result">
    Parse the JSON body. Branch on success (`2xx`) or error (`4xx`/`5xx`) status codes.
  </Step>
</Steps>

## Implementation Example

```javascript
// Fetch a customer record synchronously and use the result immediately
async function getCustomer(customerId) {
  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), 8000); // 8-second timeout

  try {
    const response = await fetch(
      `https://your-instance.webbab.se/api/resource/Customer/${customerId}`,
      {
        headers: {
          'Authorization': `token ${process.env.WEBBAB_API_KEY}:${process.env.WEBBAB_API_SECRET}`,
          'Content-Type': 'application/json',
        },
        signal: controller.signal,
      }
    );

    clearTimeout(timeoutId);

    if (!response.ok) {
      const error = await response.json().catch(() => ({}));
      throw new ApiError(response.status, error.exc_type ?? 'UnknownError', error.message);
    }

    const { data } = await response.json();
    return data;

  } catch (err) {
    clearTimeout(timeoutId);
    if (err.name === 'AbortError') {
      throw new Error(`WEBBAB request timed out after 8 seconds`);
    }
    throw err;
  }
}
```

## Timeout Handling

Always set an explicit timeout. Without one, a network partition or slow WEBBAB response can leave your application waiting indefinitely.

| Scenario | Recommended timeout |
|---|---|
| Simple record fetch | 5–10 seconds |
| Create / update with validation | 10–15 seconds |
| Report or large list | 30–60 seconds (or switch to async pattern) |

Handle `AbortError` / `TimeoutError` separately from application errors so you can retry safely:

```javascript
try {
  const customer = await getCustomer('CUST-00123');
} catch (err) {
  if (err.message.includes('timed out')) {
    // Safe to retry — the original request may or may not have reached WEBBAB
    // For non-idempotent operations (POST), check before retrying
    await retryWithBackoff(() => getCustomer('CUST-00123'));
  } else {
    throw err;
  }
}
```

## Error Propagation

Propagate WEBBAB errors back to the caller with enough context to act on them. Map HTTP status codes to meaningful application-level errors:

```javascript
class WebbabApiError extends Error {
  constructor(status, code, message) {
    super(message);
    this.status = status;
    this.code = code;
  }
}

function handleApiResponse(status, body) {
  if (status === 401) throw new WebbabApiError(401, 'AUTH_FAILED', 'Invalid API credentials');
  if (status === 403) throw new WebbabApiError(403, 'FORBIDDEN', 'Insufficient permissions');
  if (status === 404) throw new WebbabApiError(404, 'NOT_FOUND', 'Resource not found');
  if (status === 429) throw new WebbabApiError(429, 'RATE_LIMITED', 'Too many requests — back off and retry');
  if (status >= 500) throw new WebbabApiError(status, 'SERVER_ERROR', 'WEBBAB server error — retry with backoff');
}
```

## Retry Strategy

Not all errors are retryable. Follow this rule:

| HTTP Status | Retryable? | Notes |
|---|---|---|
| `200` | — | Success |
| `400` | ❌ | Bad request — fix your payload |
| `401` | ❌ | Credentials invalid — do not retry without new token |
| `403` | ❌ | Permission denied — retrying will not help |
| `404` | ❌ | Resource does not exist |
| `429` | ✅ | Rate limited — use `Retry-After` header or exponential backoff |
| `500` | ✅ | Server error — retry with exponential backoff |
| `502` / `503` | ✅ | Gateway/service unavailable — retry with backoff |
| Timeout | ✅ | For idempotent reads; use caution for writes |

<Warning>
Be careful retrying non-idempotent operations (`POST` to create a resource). A timeout does not mean the request failed — WEBBAB may have received and processed it. Check for an existing record before retrying a create operation.
</Warning>

## Strengths

- **Simple mental model** — straightforward request-response is easy to reason about and test
- **Immediate feedback** — errors surface instantly to the caller
- **No infrastructure overhead** — no queues, brokers, or workers to manage

## Limitations

- **Latency coupling** — your application's response time is directly tied to WEBBAB's response time
- **Fragility** — a WEBBAB outage blocks your workflow
- **Not suited for high throughput** — each call ties up a connection and a thread/coroutine

## Security Considerations

- Store API credentials in environment variables or a secrets manager — never in source code
- Use HTTPS for all requests (enforced by WEBBAB)
- Rotate API keys periodically and revoke old ones immediately after rotation
- Scope API keys to minimum required permissions
- Log WEBBAB API errors but never log the full `Authorization` header
