Your WEBBAB API key and secret are the keys to your tenant's data. Anyone who holds them can read, create, update, and delete records according to the permissions of the associated user. Treat them with the same rigour you would treat a master password — generate them carefully, store them securely, rotate them regularly, and revoke them the moment they are no longer needed.

## Credential Types

WEBBAB uses a two-part credential: an **API key** (a public identifier) and an **API secret** (a private authenticator). Both are required on every request. Together they form the `Authorization` header value.

```
Authorization: token YOUR_API_KEY:YOUR_SECRET
```

| Component | Purpose | Exposure |
|---|---|---|
| API Key | Identifies the user account | Can appear in logs — not secret on its own |
| API Secret | Proves possession — never shared | Must never appear in logs, code, or URLs |

<Warning>
  The API secret is shown only once at generation time. Store it immediately in your secrets manager. If you lose it, you must regenerate the key pair — there is no way to retrieve the secret after initial display.
</Warning>

## Generating Credentials

<Steps>
  <Step title="Create a dedicated API user">
    In the WEBBAB admin panel, create a user account dedicated to your integration. Name it clearly (e.g. `crm-sync@yourapp.com`) so its purpose is obvious in logs and audit trails.
  </Step>
  <Step title="Assign the minimum required role">
    Before generating the key, assign only the roles your integration needs. See [Permission Model](/security/permissions) for least-privilege guidance.
  </Step>
  <Step title="Generate the API key and secret">
    In the user's profile, generate an API key. The secret is displayed once — copy it immediately.
  </Step>
  <Step title="Store the secret securely">
    Paste the secret directly into your secrets manager or environment variable store. Do not write it in a text file, email, or chat message.
  </Step>
</Steps>

## Secure Storage

Never hardcode credentials in your application source code or configuration files. Use one of the following storage mechanisms:

### Environment Variables

The simplest secure approach for most deployments. Set variables in your deployment environment and read them at runtime.

<CodeGroup>
```bash Set environment variables (Linux/macOS)
export WEBBAB_API_KEY=YOUR_API_KEY
export WEBBAB_API_SECRET=YOUR_SECRET
export WEBBAB_BASE_URL=https://your-instance.webbab.se
```

```python Read from environment (Python)
import os
import requests

api_key = os.environ["WEBBAB_API_KEY"]
api_secret = os.environ["WEBBAB_API_SECRET"]
base_url = os.environ["WEBBAB_BASE_URL"]

response = requests.get(
    f"{base_url}/api/resource/Customer",
    headers={"Authorization": f"token {api_key}:{api_secret}"}
)
```

```javascript Read from environment (Node.js)
const apiKey = process.env.WEBBAB_API_KEY;
const apiSecret = process.env.WEBBAB_API_SECRET;
const baseUrl = process.env.WEBBAB_BASE_URL;

const response = await fetch(`${baseUrl}/api/resource/Customer`, {
  headers: {
    Authorization: `token ${apiKey}:${apiSecret}`
  }
});
```
</CodeGroup>

### Secrets Managers

For production systems, use a dedicated secrets management service:

| Platform | Service |
|---|---|
| AWS | Secrets Manager or Parameter Store (SecureString) |
| Google Cloud | Secret Manager |
| Azure | Key Vault |
| HashiCorp | Vault |
| Kubernetes | Sealed Secrets or external secrets operator |

<CodeGroup>
```python AWS Secrets Manager (Python)
import boto3
import json

def get_webbab_credentials():
    client = boto3.client("secretsmanager", region_name="eu-north-1")
    secret = client.get_secret_value(SecretId="webbab/api-credentials")
    return json.loads(secret["SecretString"])

creds = get_webbab_credentials()
api_key = creds["api_key"]
api_secret = creds["api_secret"]
```

```javascript AWS Secrets Manager (Node.js)
const { SecretsManagerClient, GetSecretValueCommand } = require('@aws-sdk/client-secrets-manager');

async function getWebbabCredentials() {
  const client = new SecretsManagerClient({ region: 'eu-north-1' });
  const command = new GetSecretValueCommand({ SecretId: 'webbab/api-credentials' });
  const response = await client.send(command);
  return JSON.parse(response.SecretString);
}

const { api_key, api_secret } = await getWebbabCredentials();
```
</CodeGroup>

## What Never to Do

<Warning>
  The following patterns are insecure and must never appear in production code, pull requests, or documentation examples.
</Warning>

```python
# ❌ NEVER hardcode credentials
api_key = "d2a3f89c1b..."
api_secret = "7f9e2a1c..."

# ❌ NEVER commit .env files with real credentials
# .env should be in .gitignore

# ❌ NEVER log credentials
print(f"Connecting with key {api_key} and secret {api_secret}")

# ❌ NEVER pass credentials as URL query parameters
# /api/resource/Customer?api_key=d2a3f89c...&api_secret=7f9e2a1c...
# They appear in server logs and browser history
```

```javascript
// ❌ NEVER expose credentials in client-side JavaScript
// Browser code is readable by anyone — never embed API secrets here
const apiSecret = "7f9e2a1c..."; // visible to all users
```

## Rotation Schedule

Rotate API credentials on a regular schedule and immediately after any of the following events:

| Trigger | Action |
|---|---|
| Scheduled rotation | Minimum every 12 months; 90 days recommended |
| Team member departure | Rotate any keys the person had access to |
| Suspected compromise | Revoke immediately; generate new pair |
| Integration decommissioned | Revoke and delete the API user |
| Repository exposed | Revoke any credentials visible in git history |

### Rotating Without Downtime

<Steps>
  <Step title="Generate a new key pair">
    Generate a new API key and secret for the API user. The old key remains active.
  </Step>
  <Step title="Update your secrets store">
    Store the new credentials in your secrets manager or update environment variables in your deployment.
  </Step>
  <Step title="Deploy the updated configuration">
    Roll out the updated configuration to your application. Verify that it authenticates successfully with the new credentials.
  </Step>
  <Step title="Revoke the old key">
    Once traffic confirms the new key is working, revoke the old key in the WEBBAB admin panel.
  </Step>
</Steps>

## Revocation

Revoke a credential in the WEBBAB admin panel by navigating to the API user's profile and deleting or regenerating the key. Revocation takes effect immediately — any in-flight request using the revoked key will receive a `401 Unauthorized` response.

<Tip>
  After revoking a key, check your application logs to confirm that no requests are still using the old credentials. Unexpected 401 errors after revocation indicate a place where the old key was stored that you missed.
</Tip>

## Logging Safely

When logging API activity, record the API key identifier for traceability but never log the secret.

```python
# ✅ Safe logging — key only, never the secret
import logging
logger = logging.getLogger(__name__)

api_key = os.environ["WEBBAB_API_KEY"]
logger.info("Making WEBBAB API request", extra={"api_key": api_key[:8] + "..."})
```
