The WEBBAB MCP server lets AI assistants and autonomous agents interact directly with your WEBBAB platform. Using the open Model Context Protocol standard, any compatible client — Claude, Cursor, VS Code, ChatGPT, or a custom agent — can read platform data, invoke business logic, and trigger workflows without custom integration code.

## What Is the Model Context Protocol?

Model Context Protocol (MCP) is an open standard, originally developed by Anthropic, that defines a structured way for AI clients to connect to external data sources and services. Instead of embedding platform-specific API calls inside prompts or writing one-off tool integrations, MCP gives every AI client a uniform interface for discovering and calling capabilities exposed by a server.

An MCP server advertises three kinds of primitives to clients:

| Primitive | Description |
|-----------|-------------|
| **Resources** | Read-only data sources the AI can access — similar to GET endpoints |
| **Tools** | Callable actions with defined input/output schemas — similar to POST/PATCH endpoints |
| **Prompts** | Pre-built instruction templates that guide the AI through common tasks |

The client connects to the server, discovers what is available, and then uses those primitives in response to user instructions. Your AI assistant handles the natural-language layer; the WEBBAB MCP server handles the structured integration layer.

## What the WEBBAB MCP Server Exposes

### Resources

Resources give AI clients read access to WEBBAB platform data. The server exposes resources for core business objects such as customers, orders, projects, and configuration data. Each resource has a stable URI and a defined content type so clients can cache, display, and reason over the data.

See [MCP Resources](/mcp/resources/overview) for the full list and URI format.

### Tools

Tools are the primary way AI agents take action inside WEBBAB. The server classifies every tool into one of three tiers:

WEBBAB MCP prompts are pre-built instruction templates that guide AI clients through common platform tasks — for example, creating a new customer with all required fields, or summarising open orders for a project.

## Use Cases

**AI assistants in customer support** — An agent connected to the WEBBAB MCP server can look up customer records, retrieve order history, and draft responses without leaving the chat interface.

**Autonomous workflow agents** — A background agent can monitor for new orders, check inventory levels, and trigger fulfilment workflows based on rules you define.

**IDE-integrated development** — Developers using Cursor or VS Code can query live platform data while writing integration code, reducing the round-trip between documentation and the actual API.

**Reporting and analysis** — Feed platform data directly into an LLM context window for natural-language summaries, trend analysis, and anomaly detection without exporting CSVs.

## Authentication

All connections to the WEBBAB MCP server require authentication. The server uses API credentials tied to a WEBBAB user account. Access is scoped to the permissions of that user, so you can enforce least-privilege access by creating a dedicated service account with only the roles it needs.

See [Authentication](/mcp/authentication) for configuration details.

## Read vs. Write Operations

The server distinguishes clearly between read and write operations.

- **Read operations** are always safe to call. They do not modify any data and do not require confirmation steps.
- **Write operations** modify platform data. They require the connecting user account to hold the appropriate write permissions. Some sensitive write operations include a confirmation step to prevent accidental changes.
- **Administrative operations** are restricted to accounts with administrative roles. They should never be exposed to untrusted agent contexts.

## Security Model Overview

The WEBBAB MCP server enforces security at multiple layers:

1. **Transport security** — All connections use HTTPS/TLS.
2. **Authentication** — Every request carries a valid API credential.
3. **Authorization** — The server maps the authenticated user's WEBBAB roles to the set of tools and resources they are permitted to call.
4. **Tenant isolation** — Each WEBBAB instance is isolated. A credential for one tenant cannot access another tenant's data.
5. **Audit logging** — Tool invocations are logged for review.

See [Security](/mcp/security) for full details and best practices.
