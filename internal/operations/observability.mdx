## Request IDs

Every HTTP request processed by Frappe is assigned a **request ID** (`X-Frappe-Request-Id`). This ID:

- Appears in the Nginx access log on each request line.
- Is injected into all Frappe log entries for the duration of that request.
- Is returned in the HTTP response headers so clients can include it in support reports.

### Finding a Request ID

From the **client side**: Most HTTP clients (browsers, Postman, API integrations) can display response headers. Look for `X-Frappe-Request-Id`.

From the **server side** (Nginx access log):

```bash
# Grep the Nginx access log for a known IP or path
grep 'POST /api/method/webbab_billing' /var/log/nginx/access.log | tail -20

# Example access log line:
# 203.0.113.42 - - [01/Jan/2024:12:34:56 +0000] "POST /api/method/webbab_billing.api.subscription.cancel_subscription HTTP/1.1" 200 512 "-" "python-requests/2.31" "req-a1b2c3d4"
#                                                                                                                                                                            ^^^^^^^^^^^^ request ID
```

## Correlation IDs

For requests that trigger background jobs, the **correlation ID** links the original web request to all background jobs it spawned. WEBBAB propagates the request ID as the correlation ID into enqueued jobs.

## Tracing an API Call End-to-End

Use this procedure to trace a specific request from the client through to the database and any downstream jobs.

<Steps>
  <Step title="Get the Request ID">
    Obtain the `X-Frappe-Request-Id` from the client's response headers or from the Nginx access log using the timestamp and endpoint path.
  </Step>

  <Step title="Search the application log">
    Filter the Frappe application log by request ID:

    ```bash
    grep "req-a1b2c3d4" /path/to/bench/logs/frappe.log
    ```

    **TODO**: If a centralised log platform is in use, use its search UI instead:
    ```
    request_id:"req-a1b2c3d4"
    ```
  </Step>

  <Step title="Identify enqueued background jobs">
    Look for `frappe.enqueue` calls in the log output from step 2. Note the `job_name` or job function path.

    Then search the worker log:

    ```bash
    grep "job_name_or_function" /path/to/bench/logs/worker.log
    ```
  </Step>

  <Step title="Check for errors">
    Look for `ERROR` level lines or tracebacks associated with the request ID in both the web log and the worker log. Frappe logs errors with `frappe.log_error()` which writes to:
    - The `Error Log` DocType in the desk (`/app/error-log`)
    - The `frappe.log` file
  </Step>

  <Step title="Review the Error Log in the desk">
    Go to **Desk → Error Log** (or `/app/error-log`) and search by date range or method name. The Error Log contains full Python tracebacks.
  </Step>
</Steps>

## Frappe's Built-in Error Log

The **Error Log** DocType in the Frappe desk captures exceptions thrown by `frappe.log_error()`:

```python
# How errors are recorded in application code
try:
    result = process_payment(doc.name)
except Exception:
    frappe.log_error(
        title="Payment processing failed",
        message=frappe.get_traceback(),
    )
```

Access the Error Log at: **Desk → Error Log** or `/app/error-log`.

Each entry contains:
- **Title** — set by the developer, describes the failure.
- **Error** — full Python traceback.
- **Method** — the request method path, if applicable.
- **Creation** — timestamp.
