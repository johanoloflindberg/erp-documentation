Plastkort.nu's event system is the backbone of real-time integration. Every time a document is created, updated, submitted, cancelled, or deleted, the platform fires a lifecycle event. You subscribe to these events by registering webhooks, and your endpoint receives an HTTP POST the moment the event occurs. This push model means your systems stay in sync without polling loops.

## Event Types

Plastkort.nu exposes the Frappe document lifecycle as subscribable events. Each event corresponds to a specific point in the document's life.

### Document Lifecycle Events

| Event | Fires when... | `docstatus` at fire time |
|---|---|---|
| `before_insert` | Just before a new document is saved for the first time | 0 (Draft) |
| `after_insert` | Immediately after the document is written to the database for the first time | 0 (Draft) |
| `before_save` | Before every save (insert or update) | 0 (Draft) |
| `on_update` | After every save completes (insert or update) | 0 (Draft) |
| `before_submit` | Before a document transitions to Submitted state | 0 → 1 |
| `on_submit` | After a document is successfully submitted | 1 (Submitted) |
| `before_cancel` | Before a submitted document is cancelled | 1 → 2 |
| `on_cancel` | After a submitted document is successfully cancelled | 2 (Cancelled) |
| `on_trash` | When a document is queued for deletion | Any |
| `after_delete` | After the document has been permanently deleted | — |
| `on_change` | After any field value changes (including via `db_set`) | Any |

<Info>
  Not every DocType is submittable. The `before_submit`, `on_submit`, `before_cancel`, and `on_cancel` events only fire for DocTypes that have submission enabled (e.g. Sales Orders, Invoices). Draft-only DocTypes fire `after_insert` and `on_update` only.
</Info>

### Document Status (`docstatus`)

The `docstatus` field indicates where a document sits in its lifecycle:

| Value | Status | Meaning |
|---|---|---|
| `0` | Draft | Editable; not yet finalised |
| `1` | Submitted | Locked; committed to ledgers or downstream systems |
| `2` | Cancelled | Reversed; no longer active |

Submitted documents cannot be edited directly — they must be cancelled first, then amended if a corrected version is needed.

## How Events Trigger Webhooks

When a document event fires, Plastkort.nu checks whether any active webhooks are subscribed to that combination of DocType and event. For each matching webhook:

<Steps>
  <Step title="Event fires">
    The Frappe controller hook runs at the appropriate lifecycle stage and the document state is captured.
  </Step>
  <Step title="Webhook entry queued">
    Plastkort.nu creates a delivery job in the background queue with the serialised document payload attached.
  </Step>
  <Step title="Worker delivers">
    A background worker picks up the job and sends an HTTP POST to your registered endpoint URL.
  </Step>
  <Step title="Response recorded">
    Your endpoint's HTTP status code and response body are logged against the delivery attempt.
  </Step>
  <Step title="Retry on failure">
    If your endpoint returns a non-2xx response or times out, Plastkort.nu retries delivery with exponential back-off. TODO — confirm exact retry count and schedule.
  </Step>
</Steps>

<Warning>
  Webhook delivery is **asynchronous**. The HTTP POST arrives after the document event completes — there may be a small delay. Do not assume real-time delivery under load.
</Warning>

## Event Payload Structure

Every webhook POST body carries a JSON payload with the following structure:

```json
{
  "doctype": "Customer",
  "name": "CUST-0001",
  "event": "on_update",
  "data": {
    "name": "CUST-0001",
    "customer_name": "Acme AB",
    "customer_type": "Company",
    "status": "Active",
    "owner": "api-user@example.com",
    "creation": "2024-03-15 10:22:00.000000",
    "modified": "2024-06-01 14:05:33.000000",
    "modified_by": "api-user@example.com",
    "docstatus": 0
  }
}
```

| Field | Type | Description |
|---|---|---|
| `doctype` | string | The DocType that the event belongs to |
| `name` | string | The unique `name` of the document |
| `event` | string | The event type (e.g. `after_insert`, `on_submit`) |
| `data` | object | Full document fields at the time of the event |

<Info>
  The `data` object contains all fields the webhook's associated user has permission to read. Fields excluded by field-level permissions will be absent from the payload.
</Info>

## Subscribing to Events

You register webhooks through the Plastkort.nu administration panel or via the API. Each webhook subscription specifies:

- **DocType** — the entity type to watch (e.g. `Customer`)
- **Event** — the lifecycle event to listen for (e.g. `on_update`)
- **URL** — your HTTPS endpoint that will receive the POST
- **Enabled** — whether the webhook is active
- **Secret** — a shared secret used to generate the HMAC signature for payload verification

<CodeGroup>
```json Create a webhook via API
POST /api/resource/Webhook
{
  "webhook_doctype": "Customer",
  "webhook_docevent": "on_update",
  "request_url": "https://your-app.example.com/webhooks/plastkort/customer",
  "enabled": 1
}
```
</CodeGroup>

See [Webhook Security](/security/overview#webhook-signature-verification) for details on verifying the HMAC signature on incoming payloads.

## Event Ordering

Events for a single document fire in lifecycle order within a single request (e.g. `before_insert` always fires before `after_insert`). However, across concurrent operations on different documents, Plastkort.nu does not guarantee global ordering of webhook delivery. Your integration should be designed to handle:

- **Out-of-order delivery** — an `on_update` from request B may arrive before `on_update` from request A if B completed first
- **Duplicate delivery** — network errors during delivery can cause the same event to be delivered more than once; make your handler idempotent
- **Missed events** — if your endpoint is unreachable during a retry window, events may be dropped after the maximum retry count is exhausted

Use the `modified` timestamp in the payload to detect stale updates and discard them safely.
